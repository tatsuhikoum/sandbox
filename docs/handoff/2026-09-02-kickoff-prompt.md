# ship-or-ask 設計・実装計画セッション用プロンプト

新しい Claude Code セッションを `ship-or-ask` リポジトリで起動し、最初のメッセージとして以下をそのまま貼り付ける。Superpowers プラグインが有効な前提。

---

# 背景

このリポジトリ `ship-or-ask` は、AI コーディングエージェントが作った変更を「自動でマージする(ship)か、人間にレビューを求める(ask)か」を判定するゲートを実装するためのものです。まだ README 以外のコードはありません。

判定基準の軸、参照した既存フレームワーク、推奨する判定フロー、未解決事項は、事前調査の結果として `docs/research/2026-09-02-ai-merge-gate-criteria.md` にまとめてあります。この文書がこのプロジェクトの一次資料です。設計や計画で迷ったら、まずこの文書に戻ってください。特にセクション 3(基準の軸)、5(推奨する判定フロー)、6(spike / bounded / architectural の扱い)、8.3(私が決める必要のある判断事項)を読んでから作業を始めてください。付録 A〜C は条件語彙やメトリクス定義の詳細で、必要なときに参照してください。

# 今回のセッションのゴール

このゲートを E2E のトレーサーブレッツとして実装するための、設計書(spec)と実装計画(plan)を作ることです。実装はこのセッションでは行いません。

トレーサーブレッツの定義は次の通りです。「エージェントが PR を開く → ゲートが判定する → 判定結果と根拠が PR に残る → shadow mode として人間がボタンを押してマージする」という一本の経路が、最小限の判定ロジックで、実際の GitHub 上で end-to-end に動くこと。判定の賢さより、経路が一周つながることを優先します。

# すでに決まっていること(再検討しない)

- 判定結果のラベル語彙は `ship` / `ask` / `shadow` の 3 値。
- 判定は 2 層構造。第 1 層は決定論的なハードルール(該当すれば即 `ask`)、第 2 層は適格性判定。LLM の判断を第 1 層に入れない。
- 最初の対象は Superpowers の分類で bounded に当たる変更だけ。spike と architectural は常に `ask`。
- 全カテゴリを shadow mode で開始する。トレーサーブレッツの段階では、ゲートが `ship` と判定しても実際のマージは人間が行う。
- 書いたエージェントは承認しない。レビュアーエージェントは実装エージェントと別コンテキストで動かす。
- 判定に使ったシグナルと理由を、判定ごとに PR 上に残す。
- 実行基盤は GitHub Actions と GitHub rulesets。DENY_PATHS 相当は rulesets 側にも二重に置く。
- Superpowers の brainstorming → writing-plans の流れに従う。新規プロジェクトなので architectural 経路を取る。

# 私が決めたいこと(brainstorming で聞いてほしい)

- トレーサーブレッツで判定対象にする「標的リポジトリ」を、この `ship-or-ask` 自身にするか、別の小さなサンプルリポジトリを用意するか。
- 第 1 層のハードルールのうち、最初の一本に入れる項目。候補は DENY_PATHS 一致、不可逆操作の検出、CI 弱体化の検出、計画外ファイルへの変更、の 4 つ。全部入れるか絞るか。
- レビュアーエージェントの判定を、最初から Claude Code の Code Review の `bughunter-severity` 出力を読む形にするか、Superpowers の code-reviewer.md をそのまま GitHub Actions 上で動かす形にするか、それとも第 1 層と CI だけで最初の一本を通すか。
- 判定ロジックの実装言語とテスト方法。
- 判定結果の出力先。PR コメント、ラベル、check run、のどれを最初に実装するか。
- 「計画」をゲートがどう受け取るか。Superpowers の plan ファイルのパスを PR 本文に書く、PR 本文に Files 欄を埋め込む、などの選択肢がある。

上記以外にも判断が必要な点が出てきたら、その場で聞いてください。私はこのセッションを見ています。質問は一度に一つずつで構いません。
